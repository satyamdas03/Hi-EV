# Migration discipline

Hi-EV uses [Alembic](https://alembic.sqlalchemy.org/) to manage the local database schema. The default database is **SQLite + sqlite-vec**, with **Postgres + pgvector** as an optional upgrade path.

## Current baseline

- Base revision: `aacdc9089a90_add_deadlines.py` — this revision is **frozen**.
- Current head revision: see `alembic history`.
- Local dev database: defaults to `~/.hiev/hiev.db` (SQLite with sqlite-vec). Set `EV_DATABASE_URL` to `postgresql://localhost:5432/hiev` to use Postgres + pgvector.
- Test database: tests use an isolated `sqlite+aiosqlite:///:memory:` database and never touch the dev database.

## Rules

1. **Never edit an already-applied migration.**
   - If you discover a bug in a migration that has already been applied to a real database, create a new migration to fix it.
   - Editing a base or applied revision is only acceptable during the prep sprint that established this policy. That exception is now closed.

2. **Generate new migrations from the models.**
   ```bash
   alembic revision --autogenerate -m "add document_chunks table"
   ```
   - Inspect the generated script before committing.
   - Remove any autogenerated noise that does not match the intended schema change.
   - Make sure `upgrade()` and `downgrade()` are symmetric.

3. **Keep migrations idempotent where possible.**
   - Prefer `IF NOT EXISTS` / `IF EXISTS` for indexes, extensions, and tables where Alembic allows it.
   - The pgvector extension is created with `CREATE EXTENSION IF NOT EXISTS vector;`.

4. **Test migrations locally before committing.**
   ```bash
   alembic downgrade base
   alembic upgrade head
   pytest
   ```
   - The test suite uses SQLite, so migration testing is the developer's responsibility.
   - If a migration depends on pgvector-specific types, verify it against a real Postgres instance.

5. **One logical change per migration.**
   - Do not bundle unrelated schema changes into a single revision.
   - Name revisions descriptively: `add_deadline_status`, `create_document_chunks`, etc.

6. **Do not commit data migrations inside schema migrations.**
   - Data backfills should live in separate `scripts/` or `ev/db/fixtures/` scripts, not in `alembic/versions/`.
   - Data migrations may reference model code by coincidence; schema migrations must not.

7. **Resetting local dev is allowed; resetting prod is not.**
   - For SQLite dev: delete the database file and run `python scripts/setup_sqlite_vec.py`.
   - For Postgres dev: `dropdb hiev && createdb hiev && psql -d hiev -c "CREATE EXTENSION IF NOT EXISTS vector;" && alembic upgrade head`.
   - For any database that contains real memory, write a new migration and follow rule 1.

## CI check (when CI exists)

A future CI job will compare each `alembic/versions/*.py` file against `origin/main` and fail the build if an already-present migration file was modified. New migration files are allowed.

## Quick reference

```bash
# See current status
alembic current

# See history
alembic history --verbose

# Create a new migration after changing models
alembic revision --autogenerate -m "describe change"

# Apply pending migrations
alembic upgrade head

# Roll back one migration
alembic downgrade -1

# Roll back to the beginning
alembic downgrade base

# Recreate the Postgres dev database from scratch
dropdb hiev
createdb hiev
psql -d hiev -c "CREATE EXTENSION IF NOT EXISTS vector;"
alembic upgrade head

# Recreate the SQLite dev database from scratch
rm ~/.hiev/hiev.db
python scripts/setup_sqlite_vec.py
```

## Why this matters

Hi-EV is a long-lived personal database. Once real memory accumulates, destructive resets become expensive. Immutable migrations are the cheapest way to keep the schema trustworthy across months and years of use.
